# Architecture — FurniTrack

## Stack
- **Flutter** (Dart) — mobile client, Material 3.
- **Firebase Auth** — email/password, one role per user.
- **Cloud Firestore** — primary data store, real-time listeners throughout.
- **Firebase Storage** — condition photos taken at delivery/pickup.

## Layered structure
```
lib/
  main.dart                # Firebase init + AuthGate (routes on auth state)
  firebase_options.dart    # generated by `flutterfire configure` — placeholder now
  models/                  # plain Dart classes, fromMap/toMap only, no logic
    item.dart
    rental_agreement.dart
    delivery_event.dart
  services/                # ALL Firebase access goes through here — screens
                            # never call FirebaseFirestore/FirebaseAuth directly
    auth_service.dart
    firestore_service.dart
    storage_service.dart
  screens/                 # one screen = one file, StatefulWidget where forms exist
    login_screen.dart
    signup_screen.dart
    home_screen.dart           # bottom nav shell
    overdue_items_screen.dart  # active + overdue rentals, search
    log_delivery_screen.dart   # conflict-checked delivery logging
    log_pickup_screen.dart     # closes rental, triggers billing reconciliation
    billing_dashboard_screen.dart
  widgets/                 # small reusable presentational widgets only
    loading_indicator.dart
    status_pill.dart
```

**Rule for the agent: keep this separation.** If you're adding a feature
that reads/writes Firestore, add the method to `FirestoreService` (or a new
service file if it's a distinct concern) — don't call
`FirebaseFirestore.instance` from inside a screen widget.

## Data model (Firestore)
```
users/{uid}
  email: string
  role: "crew" | "ops"

items/{itemId}
  name: string
  category: string
  dailyRate: number
  status: "available" | "rented"

rentals/{rentalId}
  itemId: string
  itemName: string          # denormalized for list display without a join
  customerName: string
  customerPhone: string
  startDate: timestamp
  expectedReturnDate: timestamp
  status: "active" | "closed"
  billingStatus: "open" | "reconciled"
  totalDue: number

deliveryEvents/{eventId}
  rentalId: string
  itemId: string
  crewId: string             # must equal request.auth.uid on create
  timestamp: timestamp
  type: "delivery" | "pickup"
  conditionPhotoUrl: string | null
  notes: string
```

### Why this shape
- `rentals.status` is the single source of truth for "is this item
  currently out" — the conflict check queries `rentals` where
  `itemId == X AND status == "active"`, not `deliveryEvents`. Events are an
  append-only log; state lives on the rental doc.
- `itemName` is denormalized onto `rentals` so list screens don't need a
  second read per row. If `items/{id}.name` changes, existing rental
  records keep the name as of delivery time — this is intentional (audit
  trail), not a bug.
- `deliveryEvents` is append-only and crew-writable only for their own
  `crewId`; only ops can edit/delete it (see `firestore.rules`), because it
  is the audit trail that resolves billing disputes.

## Core flows (already implemented, don't re-architect without reason)

### Log a delivery (`FirestoreService.createRental`)
1. Query `rentals` for an existing `active` rental with the same `itemId`.
2. If found → throw `SchedulingConflictException` (caught in the UI,
   surfaced as a red SnackBar, no write happens).
3. If clear → write the new `rentals` doc, then update `items/{id}.status`
   to `"rented"`.
4. UI then uploads the condition photo (if any) to Storage, keyed by the
   new rental ID, and writes a `deliveryEvents` doc of type `"delivery"`.

### Log a pickup (`FirestoreService.closeRental`)
1. UI uploads condition photo (if any), writes a `deliveryEvents` doc of
   type `"pickup"`.
2. Update `rentals/{id}`: `status: "closed"`, `billingStatus: "reconciled"`,
   `totalDue: <computed>`.
3. Update `items/{itemId}.status` back to `"available"`.

### Live views
- `activeRentalsStream()` — `rentals` where `status == "active"`, ordered by
  `expectedReturnDate`. `overdueRentalsStream()` filters that stream
  client-side on `isOverdue` (a computed getter on `RentalAgreement`, not a
  stored field — don't add a stored `isOverdue` field, it'd go stale).
- `openBillingStream()` — `rentals` where `status == "closed" AND
  billingStatus == "open"`.

## Firestore indexes
`activeRentalsStream` and `openBillingStream` use compound where+orderBy /
multi-where queries. When you deploy, Firestore will throw a
"requires an index" error with a direct console link the first time each
query runs — follow it, don't hand-write `firestore.indexes.json` unless
asked to.

## Security rules
See `firestore.rules`. Summary: any signed-in user can read; `items`
writes are ops-only; `rentals` create/update is any signed-in user (crew
needs this to log deliveries/pickups) but delete is ops-only;
`deliveryEvents` create is restricted to `crewId == request.auth.uid`,
update/delete is ops-only.
